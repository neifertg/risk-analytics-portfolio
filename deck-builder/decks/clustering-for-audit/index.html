Part 1

Why clustering fits audit work

Most audit populations have no label marking which record is the problem.

Supervised methodsClustering (unsupervised)
Need labeled examples: known fraud, known control failuresNo labels required
Learn to repeat a pattern you've already seenGroup records by similarity, then let the odd ones stand out
Only as good as your past examplesCan surface a pattern you've never seen before

Most audit testing starts from a population with no 'bad' column to learn from.

This is the core motivation for using clustering in audit: fraud/error labels are rare, expensive, or don't exist yet for a new risk area. Clustering doesn't need them.

Part 2

Four techniques, four audit questions

K-Means sorts records into a fixed number of segments so the odd segment stands out.

Nearest-centroid assignment, recomputed until stable — you choose k up front.

Audit use: segment vendors or transactions to find the outlier segment. Limit: requires choosing k upfront; assumes round, evenly sized groups. Source: wiki resources/k-means-clustering.md. Good fit: exploratory grouping of numeric data, e.g. customer/vendor segmentation. Poor fit: unknown k, non-round clusters, categorical-only data.

Hierarchical clustering builds a tree of groupings, so you decide the count last.

Repeatedly merges the two closest clusters — you decide the count after seeing the tree.

Audit use: explore population structure before setting a testing plan. Limit: O(n²) cost — doesn't scale to a full population; an early bad merge can't be undone. Source: wiki resources/hierarchical-clustering.md. Good fit: don't know k in advance, want to see nested structure, need deterministic results (no random init unlike K-Means). Poor fit: large datasets, noisy data with single linkage.

DBSCAN separates dense, ordinary activity from outliers automatically.

Dense regions become clusters; sparse points are flagged as noise automatically.

Audit use: auto-flag transactions or log entries that fit no normal pattern. Limit: struggles with mixed-density populations; radius/threshold settings are fiddly. Source: wiki resources/dbscan.md. Good fit: arbitrary-shaped clusters, automatic outlier detection, unknown cluster count. Poor fit: high-dimensional data, mixed-density clusters.

Gaussian Mixture Models assign each record a probability of risk instead of a hard yes/no.

Each record gets a probability of belonging to each group, not a hard label.

Audit use: risk-score records instead of a hard flag. Limit: needs more data than K-Means; easy to overfit the wrong number of components. Source: wiki resources/gaussian-mixture-models.md. Good fit: overlapping/elliptical clusters, soft assignments, varying cluster sizes. Poor fit: small datasets, no good guess for component count, very high feature counts.

K-Means

  • You choose the number of groups up front
  • Fast, scales well
  • Assumes round, evenly sized groups

Hierarchical

  • You choose the number of groups after seeing the tree
  • Deterministic, no random start
  • Doesn't scale to a full large population

DBSCAN

  • The technique finds the number of groups itself
  • Flags outliers automatically as noise
  • Struggles with mixed-density populations
Choosing among the three is mostly about whether you already know how many groups you're looking for, and whether automatic outlier-flagging matters more than speed.
O(n²)

the memory and compute cost of hierarchical clustering — a real limit when testing a full transaction population rather than a sample.

From wiki resources/hierarchical-clustering.md. Practical implication for audit: hierarchical clustering is well suited to exploring a sample or a narrowed-down population, not a full year of transactional detail. K-Means or DBSCAN scale further.

Part 3

Applying it: business and IT audit examples

Clustering vendor payments can surface the one vendor that doesn't look like the rest.

Illustrative example — not a specific finding.

Population: vendor payment records for a business cycle. Features: amount, frequency, approval path, vendor age, payment timing. This is a generic teaching example, not drawn from a real audit or organization. Adapt the population and features to whatever business-cycle data the department actually has. A flagged vendor is a lead to investigate, e.g. for duplicate payments or a shell-vendor risk — not a conclusion on its own.

Clustering access logs can flag the one account that doesn't match its peers.

Illustrative example — not a specific finding.

Population: access logs or privileged-account activity, IT general controls. Features: login times, systems accessed, transaction types, peer role. This is a generic teaching example, not drawn from a real audit or organization. Peer-group definition (e.g. by role or department) matters a lot here — cluster within a peer group, not across the whole population. A flagged account is a lead, e.g. excessive access or a compromised credential — not a conclusion on its own.

Part 4

Where to start

A first clustering pilot, end to end

1. Pick a population
One with no existing 'bad' label — a vendor master, an access log, an expense population
2. Choose features
A handful of numeric fields that describe behavior, not identity
3. Run and review
Try K-Means or DBSCAN first; read the outlier group, not just the average
4. Fold into testing
Treat flagged records as leads for existing substantive procedures, not a final conclusion
This mirrors the make-deck render pipeline's own philosophy: start from the simplest version of each piece, and only add complexity (hierarchical, GMM) once the first pass earns it.

Clustering turns 'we don't know what we're looking for' into a testable question.

Pick one dataset without a fraud label and run a first K-Means or DBSCAN pass this quarter.

Start small: one population, one technique, one review of the outlier group. The four techniques and PATTERN.md-style layout choices in this deck are illustrative — expect to adapt features and thresholds to the actual data in hand.
